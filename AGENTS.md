# Gunslinger — agent guide

## Primary goal: next-generation FPS, best-in-the-world hyperrealism

**Build a next-generation first-person shooter with utterly gorgeous, incredibly polished, best-in-the-world hyperrealistic graphics fidelity.** This is the project's primary product goal. Treat it as a guiding requirement for architecture, rendering, assets, animation, effects, interaction, and quality assurance.

Aim for the visual credibility, production detail, responsiveness, and audiovisual cohesion of an exceptional contemporary AAA shooter. Every graphics change should make the actual game more convincing at normal play distances and in motion. Judge progress through rendered evidence and hands-on play.

The current browser game is a working foundation: a procedural harbor, machine enemies, an inherited renderer, projectile combat, and a small custom gameplay layer. It has substantial distance to travel toward the target. Preserve useful behavior while deliberately improving the weakest visible foundations. The architecture, asset pipeline, and tooling may evolve when that advances the goal.

Keep the distinction between aspiration and implementation precise. Production-quality geometry, materials, lighting, animation, and scene composition require substantive work. Describe improvements honestly and identify what remains below the target.

## Visual and experiential quality bar

| Area | Standard to work toward |
| --- | --- |
| World and assets | Believable real-world scale, strong silhouettes, convincing construction, rich close-up detail, coherent environmental storytelling, and variation that holds up across a whole scene. |
| Materials | Physically credible base color, roughness, metalness, normals, and surface response. Consistent texel density and texture scale. Wear, dirt, moisture, and damage should follow material and environmental logic. |
| Lighting | Coherent sun, sky, indirect illumination, shadows, contact, reflections, and exposure. Preserve readable detail across bright exteriors and shaded interiors. Ground objects in their surroundings. |
| Image quality | Resolve aliasing, shimmer, flicker, texture repetition, z-fighting, halos, clipping, and unstable reflections. Inspect movement as carefully as still frames. Use optical effects with restraint. |
| First-person presentation | Excellent weapon and hand models, convincing animation and transitions, responsive aiming, synchronized recoil and sound, and polished impact feedback. The weapon occupies the foreground continuously; small flaws matter. |
| Interface and audio | Clear, restrained harbor-operation styling; legible combat information; consistent controls and feedback; convincing spatial sound and timing. Respect focus, reduced-motion preferences, and supported input methods. |
| Performance | Stable frame pacing and responsive controls on documented target hardware. Establish hardware, resolution, quality settings, and a frame-time budget; measure quality and cost together. |

Prioritize the largest perceptual weaknesses. Improve geometry, materials, illumination, composition, and motion directly. Bloom, grain, chromatic aberration, sharpening, and darker exposure cannot carry the visual ambition on their own.

For substantial visual work, establish representative reference views and capture comparable before/after evidence. State the remaining compromises. A striking title-screen image alone does not establish gameplay quality.

## Run and verify

Run commands from the repository root; several test fixtures read paths relative to the working directory.

| Command | Purpose |
| --- | --- |
| `npm start` | Serve the project with Node (`tools/serve.mjs`) at `http://localhost:8080`, bound to `127.0.0.1`. The page now loads about thirty scripts at once, which Python's `http.server` drops on Windows; `python3 tools/serve.py` still works where it does not. |
| `npm test` | Run the Node built-in test runner over `tests/*.test.cjs`. |
| `npm run check` | Parse-check the engine bundle and every script under `src/`, `src/vigil/`, `tools/` and `tools/desktop/` (`tools/check.mjs`). |
| `npm run desktop` | Build the Windows desktop app into `dist-desktop/` (`tools/build-desktop.mjs`: the hosted build wrapped in Electron). Needs `sharp` and `@electron/packager` on `NODE_PATH`, installed outside the repo. |
| `node --test tests/weapon.test.cjs` | Run a focused regression check against the actual bundled weapon implementation. |

The current project has no declared npm dependencies, package-install step, build step, bundler, or transpiler. It needs Node/npm for the server and checks and a desktop browser with WebGL 2 for the game. Two optional tools want the `sharp` package installed ad hoc: `tools/build-host.mjs` (the hosted build) and `tools/zombie-art/` (the Churchyard's body textures). Serve it over HTTP so relative assets load correctly. Google Fonts is optional; system-font fallbacks are already defined.

Use the current lightweight workflow while it serves the task. When introducing dependencies, build tooling, or an asset pipeline, make the change intentional and reproducible, update the commands and documentation, and retain a clear way to run the game.

### Maps

`window.GunslingerMap` is `null` on the Harbor and the active map object otherwise; it must be set before the engine script is parsed. The bundle consults it at ten narrow hook points, all no-ops when it is `null`: `bootText`, `createLevel` / `createBackdrop` / `createGround` / `createEnemies` (in `cL`), `skyFragment()`, `horizonGLSL`, `shadowBounds`, and `configure(internals)` just before `cL()` runs. Separately, the renderer's interior probe capture (`J`, `captureInteriorProbe`) takes an optional `level.interiorProbe` position; without one it uses the centre of the first interior box, which on the Churchyard is inside the crystal. `configure` hands out engine tables by name (`ut`, `Kn`, `Z0`, `T0`, `zi`, `jr`, `p_`, `ug`, `cn`, `g_`, `Ir`, `fE`, `tv`, `Gw`, `cs`, `xi`, `lb`, `Vu`, `Dz`) and a `setNav` that reassigns `Ll`, `wk`, `ru`, `Ek`, `f0`, `co`. A bundle replacement or symbol rename must carry these across; `tests/vigil.test.cjs` checks both the untouched Harbor and the reconfigured Churchyard.

The gameplay and visual layers honour a few things a map may set: `arsenal` on the map object, either `false` (no arsenal: `armed` is false and `g.arsenal` absent) or a plan for running it under the map's rules (`roster`, `numberKeys`, `gunsmithKeys`, `laserKey`, `weaponLight`, `slots`, `keepOnReset`, `swapRigs`; documented where `plan` is read in `src/gunslinger.js`). With a plan, the map's director sets `g.arsenalOwns(id)`, `g.arsenalLeave(cfg, rig)` and `g.arsenalEnter(cfg, rig)`, which bracket every weapon change on a rig (selection, `g.arsenal.load`, gunsmith rebuilds) so the map can keep its own ammunition and write its own numbers onto `rig.def`/`rig.slot`. The Churchyard does this: its kits are arsenal weapons bought during the night (only the sidearms are carried from the start), and `src/vigil/director.js` owns damage, rate, spread and ammunition. Also `g.noFireSelect`, `g.meleeKey`, `g.noDressing`, `g.gsDressLabel` and `g.moveScale` in `src/gunslinger.js`, and in `src/visuals.js` a map supplies `look(g)`, may supply `shadowFocus` (its own focused, texel-snapped shadow fit) and `viewLights` (the weapon's fill lights), and skips the harbor-only installers (ground, sea, enemy realism, practical lights, the yard environment probe). `__G.visuals.shadowFit = false` restores the engine's own shadow fit for comparison. After `brand()`, the installer calls `window.GunslingerMenu.install(g)` and the map's own `install(g)`. Changing map reloads the page.

Adding a light to the scene recompiles every shader; the Churchyard keeps a fixed, small set for that reason. Check boot time on both maps after touching lights or material variants.

The bundle carries additions for the controls and the warm-up (`tests/controls.test.cjs` checks each anchor). On `g.input`: `bindings` (the key table) and `act(source, action, down)` (anchor `uiPressed(ne){return h.has(ne)},bindings:fE,act:v,rumble:Y,`); `padOwn`, which stops the engine mapping controller buttons to actions while it still reads the sticks, runs its own menus and rumbles (`if(!m.padOwn){let Ge=D(ye.buttons[2]);`); `padSens` and `padInvert` for the right stick; `uiHold`, which stills the engine's own menu navigation (`function X(){!r.uiPressed||r.uiHold||`); `padGlyph` / `keyGlyph`, what the interact prompt shows; `freeCursor`, which stops the engine pausing when the mouse is let go in play (the gunsmith sets it: without it, opening the gunsmith with the mouse captured paused the game and closed the gunsmith). On `g.render`: `hold`, which stops the resolution scaler and the automatic quality drop from counting frames (`if(Q.hold){S.acc=0,S.n=0,...`).

The bundle carries four more additions that belong to no map. `g.audio.mix` is `{ master, music }`: the input of the master chain and the node the music bus feeds (anchor `duck:k,buses:z,mix:{master:E,music:U},update:we,`); a map's own music connects to `mix.music`, and `src/vigil/music.js` falls back to the `dry` bus when it is absent. And `g.game.title()` returns to the title screen from `paused`, `dead` or `complete` (anchor `pause(){le()},resume(){xe(!1)},`). `src/menu.js` adds a Main menu button to those three cards that calls it, and the Churchyard's director clears its dead and defenses on the `title` state. `g.audio.titleRain` (0.5) scales the two rain loops while the state is `title` (anchors `update:we,ready:v,selfTest:Ae,titleRain:.5,` and the two `setGain` calls beginning `vi.rain.setGain(B*(1-.93*se)*.95*(de==="title"?`). And the player's muzzle-flash light takes its reach and hold from the weapon's `def.flashReach` / `def.flashHold` (anchor `lightPool.flash(A,16756832,Y.flashLight,Y.flashReach||9,Y.flashHold||.05)`); `GunslingerArsenal.flash` (`scale`, `light`, `reach`, `hold`) is what `compose` multiplies and writes there. `tests/mixer.test.cjs` checks all of these anchors.

Recoil: the armed branch of `src/gunslinger.js` wraps `p.addRecoil` and scales the engine's kick by `g.recoil` (`pitch`, `yaw`, and `ads`/`crouch` factors) on top of the held weapon's own `recoil`; `applyTuning` sets `recoilKeep` to 0.65, so about two thirds of each kick stays as climb. The Churchyard's director wraps it again with `recoilK()` (the kept tree's Steady Aim, the night's Steady Hands, the Recoil Harness perk, Adrenaline). Measure a change by reading `p.pitch` round each `addRecoil` call; in a headless run the cursor moving also turns the view, so do not read climb across a mouse move.

A prism sight (the TA-31, `prism: true`) is looked through rather than replaced by the scope overlay. Its model is solid with dark glass, so `buildParts` adds one depth-only disc (`colorWrite: false`, `renderOrder` −100) just behind the reticle lens; `parts.setAim(level)`, called from the frame wrapper in `src/gunslinger.js`, shows it and hides the dark ocular once the weapon is more than half aimed, and everything of the weapon behind it fails the depth test so the world shows. Keep that disc drawn before every other mesh on the weapon's layer.

The Churchyard's rain is the engine's with its streak shader rewritten (`V.heavyRain` in `src/vigil/ground.js`, numbers in `RAIN` there): longer, wider streaks, a second mesh on the same geometry with a wider box, light from the four lamp slots and the flashlight (`V.world.lights`), and `uFlash` for lightning. It replaces exact lines of the bundle's shader and throws if one is missing; `tests/vigil.test.cjs` runs it against the bundle's text. The engine's reload refuses when `reserve <= 0`, and on the Churchyard every reserve is 0: that is how nothing is ever reloaded there (never `null`, which the engine also reads as nothing).

### Soldiers, challenges and boards

The installer in `src/gunslinger.js` calls `GunslingerMixer.install(g)`, `GunslingerAlerts.install(g)` and `GunslingerCharacters.install(g)` before `brand()`, and `GunslingerProgress.install(g)`, `GunslingerLocker.install(g)` then `GunslingerSkillTree.install(g)` after the map's own `install`. The achievements document carries other parts of the save through `A.extra(name, { doc, merge, dirty, saved })`; `src/progress.js` registers `level` and, on the Churchyard, `skills`, awards experience where it reports facts, and sends announcements to the lane. All of them are optional: without the soldier file the co-op avatars fall back to the watchman's body and the Operator button is absent.

A soldier's bones are placed in world coordinates and its root never moves, so an actor's root must stay at the origin of an untransformed group: place actors with `place()`, never by moving `actor.root`. `GunslingerCharacters.update` runs from its own `render.frame` wrapper, menus included; `defenses.js` poses each hired guard's actor where the guard's placement group stands (`poseGuard`; the group is still what the rest of that file moves, turns and removes, through `drop`), and `net.js` places each remote player's actor from the room's state (the player entity carries the outfit id as `o`; an unknown id falls back to Assault). Outfit materials are one shader program for all outfits (`HOST.shader` in `src/characters.js` adds dirt, fade and rain; its anchors are checked and throw if three.js renames them). The rifle in a soldier's hands is the engine's first-person rifle geometry (`g.weapon.rigs.rifle.root`) with plain materials; if the rig changes shape, check `rifleParts()` and the grip points in `HOST.grips`.

The Operator screen takes the camera while it is open (`stageFrame`: position, `lookAt`, `setViewOffset`) and gives it back on close; a map names its spot with `map.stage = { at, cam, turn, fov, key }` or uses `STAGES` in `src/characters.js`. Its key light is one of the engine's pooled lights (`render.lightPool.acquire()`), so nothing recompiles. A map may also set `map.soldierLook`.

Facts are reported from `src/progress.js`: the Harbor's kills are resolved a microtask after `enemy:killed` so the bullet's `player:hitEnemy` or the barrel's `explosive:blast` of the same instant is known. Small events exist only to be counted: `gs:dressing` (`src/gunslinger.js`, and the Churchyard's medkit), `vigil:placed` (`defenses.js`), `vigil:stacked` and the `first`/`k` fields of the wave's `objective:done` (`director.js`), `blast` on the Churchyard's `enemy:killed` (`zombies.js`). When adding a challenge, add its fact's report in the same change: `tests/progress.test.cjs` fails if a challenge waits for a fact nothing reports. A run's standing is sent while it is played, not only at its end (`live()` in `src/progress.js`: on a wave cleared, on pause, when the tab is hidden, and every `LIVE_S` seconds of play): only boards whose score can only grow during a run, each only once the run has passed what it last sent (`R.sent`), with career kills given back to the counter if the send fails. A new board that should update in play is added to `live()`. Scripted runs must use `?noboards=1`: board entries cannot be deleted.

### Churchyard layout and how the dead find their way

`V.CH` (in `src/vigil/map.js`) is the church's outer half extents; the tower, buttresses, roof, pews, supplies, paths, grave placement and grass all derive from it, so change the church there and not by moving one wall. `church.build` returns `entrances`: one rectangle on the ground per way in (`south`, `west`, `east`, `north`; `wide` marks the two the abomination uses). `yard.build` returns `graves` and `crypts` (where a body walks out of a mausoleum: `from`, `to`, `sill`, `inside`), and `OPENINGS` lists the gates and breaches of the graveyard wall, three a side.

The dead do not use the engine's navigation grid. `makeNav` in `src/vigil/zombies.js` (`V.zombieNav` for tests) rasterises the same colliders with a 0.3 m margin: a collider blocks them unless it is `noNav`, `bulletOnly`, lower than 0.47 m or wholly above 1.5 m. A low platform they should walk over (the altar dais) is therefore `noNav`; a heap they should walk round needs a collider at least that high. It then builds, for every entrance, `LANES` flow fields to the crystal over ground whose cost varies with slow noise and rises next to obstacles, with other entrances' thresholds penalised. Each zombie gets a route (`nav.route`: nearer and emptier ways in are likelier), a lane, a sideways offset it keeps wherever there is room (`nav.room`), and a gait (`GAIT`); `sway` adds the weave, the flanking of a living target and the lean away from neighbours, and `nav.nearer` makes one that passes another open door take it. One plain field (`crystalField`) remains for reachability and as the fallback, and each player has a field of their own.

The dead come in three sizes (`SIZES` in `zombies.js`, `V.zombieSize(type)`): everything up to a spitter walks the grid above; a brute and the abomination each have a grid of their own, cut with their own radius plus 0.12 m and their own height, with one field per way in, a plain field to the crystal and, while one of that size is alive, a field toward each player. In those grids `noNav` does not exempt a collider that stands more than a step (0.42 m) high: a thin post, a door leaf and a lintel below the body's head all block, which is how the abomination is kept out of the side doors (their lintel collider starts at 3.5 m) without being told. `nav.usable(route, size)` says whether a size can come in by a way; `nav.route`, `nearer`, `field`, `dirAt`, `free`, `room`, `fieldOf` and `crystal` all take the size. A grid cell is half a metre, so a size is only certain of an opening wider than its diameter plus about 0.75 m: keep 1.9 m clear for a brute and 2.4 m for the abomination wherever they are meant to pass, and put nothing thin in the middle of such a way (a candelabrum inside the breach once stopped every abomination that came in by it). A body that means to walk and gets nowhere for two seconds counts as stuck whatever its speed reads; one that cannot reach a player gives up on players for eight seconds and goes for the crystal.

A type in `V.ZOMBIES` either has kinds of its own in `figure.js` (`KINDS`: a mesh and a painted atlas each) or borrows one with `body`, tinted (`tint`), its eyes recoloured (`glow` multiplies the borrowed body's), with anything else bolted to its bones in `make()` (the wolf's muzzle, ears, jaw and tail: `wolfParts`). The wolf, the burster and the pyre are borrowed bodies, so they needed no new artwork; a new kind with its own look needs an atlas from `tools/zombie-art`. Bodies are pooled by type and kind. What sets a type apart is read off its config where the manager already decides things: `fours` (posed by `foursPose`, capsule `tall`), `leap` (a moment sunk, then an arc of its own: `startLeap`, `leapHit`), `burst` (a fuse lit in reach, then `kill` with `self`; any kill but a head shot queues a smaller one in `blasts`), `spit.splash` (a bolt of fire instead of bile), `burning`, and the abomination's `fire` (`bossFire`: `aura`, `nova`, `bolts`). `scorch()` is the one place fire and blasts hurt anything. A snapshot record is 13 characters: the last carries the type (four bits), whether it is wreathed in fire and whether it is in the air; a nova goes to the other machines as the `zf` message and a bolt as `sp` with its splash as a seventh number. When adding a type, add it to `KILL_NAMES` (`src/progress.js`), `XP` (`src/levels.js`), `V.LIFE.worth`, `holdout.killScore` and `composeWave` (`director.js`), and to the tests that list the types.

Five types are not walkers. `fly` in a config (demon, skull, bat) sends a body through `stepFly` instead of the ground steering: with a line of sight it does its own business (`fs`: the demon orbits and spits, the bat `orbit`/`dive`/`climb`, the skull `seek`/`wind`/`charge`/`rest`); without one it drops to `V.FLY.low` and follows the small dead's flow fields. It moves with `moveCapsule` as a capsule round its body (`centre` ± `half`) and is clamped between `V.FLY.clear` and `V.FLY.top` above the floor. The roofs have no colliders, so that ceiling, below the eaves, is what keeps flyers out of them: do not raise it past the wall tops. `pos` of a flyer is a point `centre` below its middle, so code that aims a metre above `pos` still works; use `Z.centreY(z)` when the height matters, and `forEachInRadius(x, z, r, fn, y)` for a test in three dimensions (a blast and a shell's fuse both pass `y`). `beast` (skull, bat, spider, greatspider) means a body from `beasts.js`: no bones, limbs or zones, hit spheres from `V.BEAST_HIT` tested through the mesh's world matrix, no ragdoll (`startCorpse` / `updateCorpses`), `sever` and `decapitate` refuse it, and its `kind` is its type. Spiders use the ordinary ground steering plus `tryClimb` / `stepClimb`: eight rays find a box at least `least` taller than the spider within `reach`, the perch must see the target, and the box is looked for in `g.physics.boxes` every frame so a wall that is broken drops the spider. `cfg.size` puts a type on a bigger size's grid. A snapshot record is 14 characters: the last is height above the floor for flyers and spiders off the ground. `pack` spawns that many together for one place in a wave's list. A skull's `charge.dead` is what its blast does to the dead (0). In `composeWave` the new kinds take `beastP` off the top from wave 4 and great spiders are a fixed count like brutes.

A zombie spawned with `roam: true` is one of the wild dead: `z.wild` stays true for its life and keeps it out of `aliveCount()` (so it never holds a wave open or counts toward its cap; `wildCount()` and `wildOf(type)` count them), and `z.roam` is true until it wakes. While it roams, `think` gives it `tk: 'roam'` and the update walks it by `roamStep` (straight lines to nearby points it can reach, never into the church) or to `z.job`, a place beside a totem. It wakes, for good, when a living player is within `cfg.aggro`, or within 70 m while `aggroT` runs (being hurt, or `Z.noise(x, z, radius)` from a shot); then it is an ordinary zombie that happens not to be counted. Anything that asks "is there a fight" (music, storm) should skip bodies with `z.roam`.

When colliders change (something breaks, a defense is placed, a run restarts) the blocked grid and the plain field are rebuilt at once and the route fields a slice a frame (`nav.tick`, about a millisecond; a full refresh takes a few seconds). Until its turn a field still leads where it did; steps into closed cells are refused. Do not make that rebuild synchronous: one weighted flood of the 256×256 grid costs 10 to 20 ms.

After moving furniture, doors or the graveyard wall, run `node --test tests/vigil.test.cjs`: it builds the real church without a GPU and fails if an entrance is narrower than four cells for the dead or if a route leaves by the wrong threshold. It also fails if a brute cannot use all four ways in, or the abomination the main door and the breach, with at least two of their own cells across the threshold. A sealed entrance does not show in play as an error, only as every zombie queueing at the others. Where the dead appear is decided in `director.js` `spawnOne` from `composeWave`'s `sectors`, `strayChance`, `riserChance` and `cryptChance`; every source keeps its distance from every living player.

### Ammunition, the pile, and what a break does

The Churchyard has no magazines. `V.AMMO` is the kinds of ammunition (`cap` carried, `unit` price a round, `short` for the HUD); a kit names its kind (`ammo`) and how many come with it (`gives`), and kits of a kind share one count. `director.js` keeps `S.ammo[kind]`, except for the kind the rifle rig holds, which is counted on the rig: `kitStats` makes the rig's magazine the whole of what is carried (`magSize` = `capOf(kind)`, `slot.ammo` = the count, `reserve` 0), the weapon wrapper writes `slot.ammo` back every frame, and `have(kind)` / `addAmmo` / `setAmmo` read and write whichever is live. Go through those, never `rig.slot` directly, when something gives or takes rounds. A sidearm's `slot.ammo` is `Infinity`. `S.kit` is `null` until a rifle is bought: guard `V.KITS[S.kit]`, and the wrapper puts the pistol back in hand if the rifle rig is ever up without one (the engine's `1` key is unbound in `map.js` for the same reason). `capOf` grows with the kept tree's Deep Pouches (`FX.reserve`) and the Bandolier perk (`extmag`); the rate of fire with `RX.rate`, `FX.reload` (Light Trigger: the id is the old reload skill's, kept for saved trees), Quick Hands and Adrenaline. The HUD's count comes from `g.gsAmmo` (a hook `src/gunslinger.js` asks for), the pools from `ui.js` (`.vg-pool`).

Ammunition is bought at the pile, not in the armory: `yard.js` builds it outside any `B.begin` (so it never breaks) and returns `pile`; within 2.3 m the director sets `S.pile = { cost, guns }` and `g.input.setPrompt(true)`, `ui.js` writes the line, and the use action (`GsUse`: E, or a controller's X while the prompt is up; `src/controls.js`) calls `buyAmmo`. `V.ammoBill(need, money)` is the arithmetic (pure, tested): everything short if it can be paid for, otherwise the same share of each kind. A saved night keeps `kits` (owned) and `ammo` (by kind); one saved before this comes back with its kinds full.

A thing that breaks goes off (`boom` in `destruct.js`, numbers in `V.BOOM`): effects, a flash from the light pool, the engine's `explosion` event, damage to the dead in reach (host only) and to this machine's player. It calls nothing that damages other breakables, on purpose: one break must not set off the next. It is skipped while `quiet` (a restore, a late joiner's sync). Broken-off pieces are `heap`ed by material and by when they broke, lie `V.DEBRIS.life` seconds from the break, sink and are disposed; small ones are loose bodies with `sinceBirth` (`phys.js`), as severed limbs are. Stumps stay (`settle`). A breakable that carries candles lists them in `flames` (entries of the level's flame list; `f[4]` set means out): `church.js` does this for the altar's candlesticks, the stand and the chandeliers. The player's jump height is `g.jumpApex` (1.35 here; the bundle reads `tuning.jumpApex` at each jump).

### What things cost: ammunition, repairs, skills; and the dash

A visit to the pile costs `V.AMMO_RISE` (20) more for each visit before it this night: `S.ammoBuys` counts the visits that bought anything (reset by a new night, kept in the saved one), and `V.ammoBill(need, money, fee)` pays the fee first when money is short. A repair is priced by what is broken: `V.repairCost(parts)` with `V.REPAIR` (`crystal`: what the whole crystal is worth; `defense`: the share of a defense's `V.DEF[kind].price` its whole mending costs). The two armory items are `partial`: `buy` in `ui.js` takes what money there is, up to the price, and the item mends that share (`D.healCrystal`, `V.defenses.repairAll(share)`; a guest asks the host with `dfix`). An armory item whose price depends on the state of things should be `partial` only if buying part of it means something. Each rank of a kept skill costs two points more than the last (`V.skillCost(id, have)`, `V.skillSpent`); a row's `cost` is its first rank's.

The dash is `startDash` in `src/gunslinger.js` (both maps; `Gunslinger.dash()`): for `g.dash.time` seconds the frame wrapper of `player.update` sets the player's horizontal velocity to `g.dash.speed` along the direction taken at the press and holds `vel.y` at zero or above, then leaves it at `g.dash.keep` (the engine would otherwise slide for most of a second: its ground deceleration is slow next to a dash). `g.dashOk` lets a map refuse one (the Churchyard: while down). The action is `dash` in `src/controls.js` (code `GsDash`; R and X on the Churchyard, where X at the pile is `use`; X and LB+X on the Harbor, where X reloads); its sound is `gs_dash` in `src/arsenal.js`.

### The gun panel, numbers off a hit, and the boss's bar

`src/gunslinger.js` draws the weapon in hand in `#gs-gun` (both maps): a cell of `assets/ui/weapons.webp` chosen by the held weapon's id (`GUN_ICONS`, the order `tools/hud-icons/build.mjs` packs them in: add a weapon to both), its name, and what `g.gsAmmoInfo()` returns (`{ n, of, frac }`; without the hook, the magazine and reserve). The Churchyard sets the hook and draws the ammunition chips (`#vg-pools`, `ui.js`). A new weapon needs an icon: render it side on, run it through the image tool with the prompt in the build script's header, rebuild the sheet. `V.ui.hit(z, amount, head)` is the number that rises off a body; the director calls it from `modifyDamage` for the player's hits, and it adds up a frame's hits on one body. `#vg-bosses` shows a bar for every living `boss` in `g.enemies.list` (up to three), read each frame, so guests see it from the replicated health. `Gunslinger.spray(auto, n)` is the shape of a burst (pure, `tests/recoil.test.cjs`); `g.recoil.ads` is above one because the engine already hands over 0.55 of a kick when aimed. A night lost sets `startWant` to the last wave of five (`crystalLost`); `respawn` puts the player at `g.level.playerStart`; down, the frame wrapper circles the camera 5.2 m from the crystal. A break is heard through `g.audio.play('explosion', ...)` and shakes the view a little at most every 0.45 s: do not emit the engine's `explosion` event from `boom`, it shakes hard and a wall is a dozen breaks. A board with words on it is `yard.signs` (`{ pos, ry, w, h, text }`), painted by `lighting.js` on an unlit plane.

### Names on the leaderboards

The service names a board row only for a claimed account. `GunslingerOnline.callsign(set)` is the name typed on the title (`#gs-name`, added by `src/menu.js` on both maps; stored under `gunslinger.name`, the key `net.js` uses for the lobby). `GunslingerBoards.publishName(rank)` packs it (`packName`: sixteen characters of forty, eight to a board, under the player's longest vigil as rank) onto `gunslinger-callsign-1` and `-2` with mode `set`; `names()` reads the top hundred of both and `top()` uses them, then a claimed `username`, then the id. Publishes are queued so the last asked for is the last sent, and `?noboards=1` mutes them. The numbers reach 8.5e15: checked exact against the live service. If the service ever offers a display name, replace this with it.

### Buildings that come down, and what else the Churchyard keeps running

`src/vigil/destruct.js` breaks buildings with the same cuts as a headstone, in larger pieces and in two goes. The level makes a building by capturing a whole section of the builder and cutting it into cells: `B.begin({ kind, hp, raze, rests, hangs, tag })` … `B.endGrid({ xs, zs, ys, capKeys, capKey, restsAbove })` in `src/vigil/kit.js` slices the captured geometry and colliders at the given planes and makes one breakable object a cell. The church's shell is one capture cut by `xs: [-3.3, 3.3]` and the six `BAYS` along z (16 bays of wall, tag `church`, 2400 hp, `raze`); the cuts are placed clear of every window, door and buttress on both walls of a pair, so move them if those move. A wall is two skins, so `capKeys` closes each cut end with a face. The roof is a second capture cut by the same `BAYS` (tag `church-roof`, `rests: ['church']`), the tower a third cut by `ys` into four tiers (`restsAbove: ['tower']`), each mausoleum one object (tag `crypt`, kept on `yard.crypts[i].body`), each door leaf and chandelier an object that `hangs` on its wall or roof bay.

What the flags mean: `raze`: after the snap the stump stays its own live object with half the hit points and can be worn down to nothing (`change(o, 'w')` from the stump state). `rests: [tags]` / `hangs: [tags]`: the tagged objects under it (or, for `hangs`, overlapping it at any height) are its `supports`; when half of them are stumps or gone it is queued in `falling` and shattered a moment later (host only: guests are told each change as usual, and `netList`/`netSync` carry the end state to late joiners and to the saved night). `smash` (the bigger dead forcing their way) skips buildings; `blast` measures to the nearest face of an object, not its centre, so a charge against a wall hurts it. `slice` copies whole triangles in runs and only works on the ones the plane crosses (a tower collapse went from a one-second freeze to about 60 ms); rubble is merged in batches of `RUBBLE_BATCH` vertices so settling a piece never re-merges everything. `vigil:broken` carries the object's `tag` and `state`. Lights and flame sprites fixed to something that falls (the chandeliers' candles) stay where they were, and rain still does not fall inside a church without a roof: both are known gaps.

Also run by `src/vigil/director.js`: `brood(dt)` lets one wanderer (`roam: true`, `emerge`) out of each mausoleum still standing every `BROOD.every` seconds, up to `BROOD.extra` more than `V.wildWanted(wave)` per house (`cryptUp(c)` reads `c.body.state`; `spawnOne` skips a fallen one too); `titleScene(dt)` keeps up to `TITLE_DEAD` wanderers in front of the title camera with the player hidden from them (`playerHidden`) and steps the manager itself, because the engine does not on the title; `V.warm` (above) borrows the same step. `V.ECON.cost` and `costNew` are what `priceOf` in `ui.js` multiplies every armory price by (a kit card marked `fresh` uses `costNew`).

The engine creates a shared runtime object, exposed as `window.__G`. It initializes rendering and game systems, calls `render.onLevelReady()`, and then calls `window.Gunslinger.install(g)`. The gameplay installer exposes `g.realism` and `g.ballistics`, installs the visual layer, and updates branding.

Important lifecycle details:

- The gameplay layer replaces `g.combat.playerShot` and `g.combat.enemyShot`, and wraps `player.reset`, `player.update`, `weapon.update`, and `render.frame`. Preserve bound calls to the existing implementations when extending these wrappers.
- The engine updates gameplay systems before invoking `render.frame`. The custom frame wrapper advances projectiles and gameplay HUD state before calling the original renderer.
- Rendering continues in menus and while paused. `g.time.t` also advances through paused frames. Gate gameplay simulation and timers explicitly; a render callback or global clock alone does not imply active play.
- `game:state` payloads contain `state` and `prev`. The custom layer clears held keys on transitions and restores combat state through its state-transition and `player.reset` hooks. Exercise retry, restart, death, completion, and redeploy after lifecycle changes.
- Installation currently adds listeners, DOM, and wrappers once. If adding hot reload or repeated initialization, implement teardown or idempotence so these do not accumulate.
- Boot can substitute stub implementations for some failed engine modules. Inspect errors and subsystem state even when a frame renders.

Keep new maintained logic readable and in `src/` where practical. Keep pure simulation independent of DOM and Three.js. Follow the existing small-function style without copying the bundle's minified naming into new code. New browser files must be included in the page and in appropriate syntax/test checks.

Treat bundle patches as narrow integration work. Locate exact anchors, explain the behavior being changed, and check affected consumers. For deeper capabilities, prefer a deliberate source/module extraction or architecture improvement that can be maintained and tested. Avoid wholesale reformatting or unrelated changes to bundled Three.js.

## Combat behavior to preserve unless intentionally changing the design

### Projectile simulation

- World units are metres and time is seconds. The solver accepts plain `{x, y, z}` vectors, normalizes firing directions, and uses swept segments to catch thin cover at high speed.
- `trace(origin, direction, range, owner)` returns a hit with `dist` measured from that segment's origin, or no hit. Engine integration also uses `point`, `normal`, `surface`, and optional `enemy`/`part` data.
- Trace cover first and limit enemy/player intersection checks to the visible segment. Cover currently stops projectiles; penetration and ricochet are not implemented.
- Defaults include gravity `9.81`, a maximum of 128 projectiles, substeps up to `1/240` second, and at most `0.1` second simulated per solver update. Long-frame behavior is therefore a deliberate consideration when changing timing.
- The integration uses projectile speeds of 820 m/s for the rifle, 360 m/s for the pistol, and 620 m/s for enemies. Damage and range also depend on the weapon-supplied options; read the full call path before tuning them.
- Damage is applied on impact. Preserve shot/hit accounting, weak-part damage, and `player:hitEnemy`/`impact` events. Do not also apply the inherited instant-shot damage path.
- The replacement `playerShot` returns `null` and `enemyShot` returns `false` while the projectile travels. They cannot synchronously report a future hit. Melee and explosions retain their inherited paths.
- Pause must freeze flight. Reset/retry must clear projectiles and relevant combat state.

### Weapons, player state, and controls

- The rifle starts automatic at 720 RPM: 12 rounds per second, including at 20 FPS. Semi-automatic fire requires new trigger edges. The pistol remains semi-automatic independently of rifle selection.
- On the Harbor `V` selects rifle fire mode; `F` is melee. Keep these actions separate. (The Churchyard remaps: `F` flashlight, `V` quick melee, `B` armory, `E` class ability, `G`/`T`/`H`/`N` items, `3`–`7` rifle kits, `2` with a sidearm out changes pistol, `Tab` gunsmith, `L` laser, `Q` rifle/sidearm, `Enter` calls a wave; see the README.) `1–6` and wheel select weapons, `Tab` / `H` opens the live modular gunsmith (blocking weapon discharge while open), `T` cycles the 3-position laser/weaponlight rotary, `I` inspects the held weapon, `R` reloads, `Q` swaps weapons, `E` interacts, and Escape pauses.
- Preserve the actual weapon's cadence, ammunition, reload, transition, and sidearm logic. A stub that counts calls cannot establish those behaviors.
- Health does not automatically regenerate. Difficulty changes can overwrite engine tuning, so `applyTuning()` deliberately reapplies the custom rules during player updates and lifecycle changes.
- Two dressings are available after reset. Holding `B` while sufficiently stationary applies one after three seconds and heals 35 health. Damage interrupts treatment. Treatment constrains firing, sprinting, and aiming.
- Sprinting consumes endurance; recovery and exhaustion use hysteresis. Critical health slows walking. Suppression affects aim; holding Alt while aiming consumes limited breath. Preserve recovery and reset behavior when tuning these systems.
- Keys and controller buttons go through `src/controls.js`: a new action is a row in its table plus the key code its listener tests for, and it must have a controller default. Read keys with `controls.listen`, not the window, or a rebind and the controller will both miss it. Touch still covers the engine's base actions only. The engine gives every enemy in `g.enemies.list` one of its machines' loops (`gull_rotor` unless the type is `hound`); `V.audio.install` asks for one by hand once, which switches that off for the Churchyard.

## Renderer and asset details that matter

**Persistent optical settings belong in `g.render.tune`.** `g.render.post` contains transient gameplay effects such as damage and fades. Writing visual-tuning fields to `post` can silently do nothing; retain the regression test covering this distinction.

The concrete extension wraps `g.ground.apron.material.onBeforeCompile`. Preserve the original hook and its uniforms, surface markings, wetness, puddles, normals, and reflection logic. The extension currently replaces the exact shader text `diffuseColor.rgb *= alb;`; a changed anchor can silently disable it. Update the program cache key when changing generated shader variants and set `material.needsUpdate` when appropriate.

The concrete texture loads asynchronously, uses sRGB color space and repeat wrapping, and caps anisotropy against renderer support. `g.visuals.materialReady` means the texture callback installed the hook; it does not prove successful GPU compilation or correct rendered appearance. A missing texture must remain diagnosable.

Impact marks reuse a bounded pool of 96 planes. Keep surface filtering, normal alignment, depth handling, and restart cleanup. `g.visuals.impacts` is an accumulated impact count, not the number of allocated meshes. Bound new transient graphics resources and give new GPU resources a clear owner and disposal lifecycle.

The local concrete image is a generated base-color asset. Preserve its provenance; it is not a scanned PBR material set. Build richer material sets and production assets as the fidelity work demands, recording origin and processing. Keep asset scale, coordinate conventions, and color-space handling consistent.

For interface work, inspect both the inline CSS in `index.html` and the later overrides in `src/gunslinger.css`. Some inherited rules use `!important`, including title typography; later normal declarations will not necessarily win. Preserve selectors and `data-*` hooks consumed by engine-generated markup. Check computed appearance, keyboard focus, narrow/short viewports, and reduced motion.

## Testing: use the right evidence

The current tests intentionally cover different layers:

- **Ballistics tests** exercise pure simulation without a renderer.
- **Integration tests** use fake DOM and engine objects to check selected gameplay rules and lifecycle behavior.
- **Weapon tests** execute the actual bundled weapon and install the gameplay layer. They protect automatic cadence at 60 and 20 FPS, semi trigger edges, selector behavior, reloads, and the pistol.
- **Visual tests** compose shader source and verify tuning destinations using engine internals. They do not compile GLSL on a GPU or judge the resulting image.

The VM harness (and `tests/vigil.test.cjs`, which loads the bundle the same way) depends on the exact engine boot expression `cL().catch(n=>yT(n&&n.stack||n));` and internal names `ut`, `I5`, `fE`, `BM`, `Nw`, `Ow`, plus the world-layout symbols `Kn`, `pw`, `hP`, `Fi`, `Ha`, `Ll`, `wk`, `ru`, and `Ek`. A bundle replacement or symbol rename requires updating that extraction. Preserve behavioral coverage when repairing the harness.

For code changes, run `npm test` and `npm run check`. Add focused behavioral regressions when changing simulation, firing, lifecycle, or shader integration. Extend existing harnesses where useful, and keep the test's claimed coverage within what it actually executes.

For graphics, UI, audio, or input changes, also inspect the game in a real browser:

1. Verify boot and asset loading; inspect console errors and module fallbacks.
2. Inspect representative exterior/interior views, ground at close and medium distance, foreground weapons/hands, enemies, shadows, reflections, and effects.
3. Test movement and aiming in motion, then relevant firing, reload, pause, retry, mission, or holdout transitions.
4. Compare images under matching camera, seed, resolution, exposure, and quality settings. Record rendering cost on identified hardware where performance is affected.
5. State exactly what was observed and what remains unverified. When browser/GPU access is unavailable, report that gap explicitly.

Do not equate a successful syntax check, a shader-string assertion, an HTTP 200 response, or `window.__ready` with verified visual quality. Audio and pointer-lock behavior require appropriate browser interaction.
